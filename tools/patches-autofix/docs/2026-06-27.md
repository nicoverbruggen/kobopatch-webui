## Method

Patches anchor on a symbol (or raw address) plus a fixed byte offset and expect a specific
call/instruction there; a firmware bump shifts those offsets. Diagnosis used `kobopatch -t`
for the failure reason, the `tools/patches-autofix/finder` helper (which reuses kobopatch's own
symbol/PLT resolver and Thumb branch assembler — now with `resolveplttail`/`findbwtail`
for tail-call veneers), `objdump` (thumbv7) + `c++filt` for disassembly, and a small Qt
resource (RCC) parser for the embedded-stylesheet case. Validation additionally ran
`kobopatch` in apply mode and compared the extracted patched ELFs byte-for-byte.
See `tools/patches-autofix/docs/FIX_PATCHES.md` for the re-runnable playbook.

## Self-maintaining conversions (should survive future firmware)

**1. "Remove PDF map widget" (libadobe, both lines).** Previously used hardcoded absolute
B.W targets and a stale `TODO: figure out what broke the plt parsing in kobopatch for
libadobe`. The real reason for raw addresses: these are Thumb→Thumb `B.W` tail-calls that
branch to the PLT *tail stub* (the Thumb veneer at `plt-4`), exactly what `SymPLTTail`
resolves. Rewritten as:

```yaml
- ReplaceBytes: {Offset: 80,  FindInstBW: {SymPLTTail: "N3AdobeReader::updatePanningMap()"}, ReplaceInstBW: {SymPLTTail: "N3AdobeReader::hideMapWidget()"}}
```

Now fully symbolic; only the in-function `Offset` (80/192) is numeric. TODO removed.

**2. "Customize ComfortLight settings" (libnickel, both lines).** Anchored on a hardcoded
address for an *unnamed* (local, no-symbol) subroutine. Replaced the raw `BaseAddress`
with a `FindBaseAddressHex` search of the 16-byte prologue
`2DE9F04F A5B006AF 0024 07F1 1006 2346`, which is unique in each binary (even a 10-byte
prefix is unique) and identical across both firmware lines. All replacements are
`Find`-guarded, so a missed match fails safely rather than corrupting code.

**3. Gesture patches (libnickel, both lines).** "Disable forward/backward swipe Gestures"
and "Disable menu swipe gesture" were converted from raw `FindH` BLX bytes to symbolic
`FindInstBLX{SymPLT}`. The WIP did this for 4.45 only; this pass also converted **4.38**
(it had been breaking on 4.38.23429/23552/23648). The call mapping, confirmed unique by
`finder` on both the newest and oldest builds:

| offset | function |
|---|---|
| 0xE8 | `ReadingView::nextPageWithTimer()` |
| 0xF6 | `ReadingView::prevPageWithTimer()` |
| 0x134 | `ReadingView::openQuickAccess()` |
| 0x13c | `ReadingView::openFooterMenuOnSwipe()` |

### What is *not* self-maintaining (and why)

**The re-targeted offset patches** (rotation, info panel, hide browser, KePub hyphenation,
adobe page numbers, My 24 line spacing) anchor on a stable named symbol but use a fixed
`Offset` + `FindInst*`. kobopatch's `FindInst*` matching is PC-relative, so the offset is
intrinsically version-specific and cannot be searched blindly. These will likely need a
small offset bump on future firmware; `finder` makes that a ~1-minute step per call-site.
Each carries an `# autofix: … last verified` annotation.

**"Remove forgot pin button from lock screen"** *cannot* be made self-maintaining with
current kobopatch primitives, and this is the most important correctness finding below.

## Forgot-pin: why it stays hardcoded

The WIP tried to convert this to `FindZlib: "#lblForgotPin[...]"`. That is impossible:

- The `#lblForgotPin` styling lives in **two byte-identical zlib streams** —
  `qss/PinCodeInputDialog.qss` (the device lock screen, our target) and
  `qss/ParentalControlPinCodeVerifyView.qss`. Identical CSS, same SHA-1
  (`0ec0849942386e73da9d40a5b873206b7720a6ff`) in **all 8 builds**.
- `FindZlib` **errors** `"substring to find is not unique"` on two matches (it does not
  pick one — confirmed by applying it). `FindZlibHash` picks the *first* match (wrong
  screen on 4.45), and because the streams are byte-identical a mis-target would
  **silently patch the wrong screen** instead of failing safe.
- Parsing the Qt resource tree (cross-checked: a `dataBase` derived from one struct node
  predicts the other's offset exactly) shows the order is **not stable across builds**:

  | Build | PinCodeInputDialog.qss (lock screen) | order |
  |---|---|---|
  | 4.45.23646 / 23684 / 23697 | 0x1CF2E51 / 0x1CF3531 / 0x1CF3531 | 2nd (higher) |
  | 4.38.23684 / 23697 | 0x19AE314 | 1st (lower) |
  | 4.38.23648 / 23552 | 0x19ADBB4 / 0x19ADE8C | 1st |
  | 4.38.23429 | 0x19B3C6E | **2nd** (flipped) |

**Both original hardcoded patches were in fact correct** (no mislabel — a hypothesis that
the RCC parse disproved). Fix: reverted 4.45 to `BaseAddress: 0x1CF3531`; 4.38 keeps
`0x19AE314`; both documented inline with the per-build offset table. Validated by applying
each (enabled, scratch copy) and confirming it modifies **only** the PinCodeInputDialog
stream on `.23697`. The address is build-specific and **fails safe** on other builds. A
genuinely portable fix would require a new kobopatch primitive that resolves a zlib stream
by Qt resource *path* (flagged, not built). On-device testing is still advisable here.

Also noted: `kobopatch -t` force-enables and tests **every** patch (even `Enabled: no`),
so the WIP's broken `FindZlib` forgot-pin *was* a real failure — the WIP shipped a **stale
empty `blacklist.json`** that masked it. After the forgot-pin fix, `test:patches:check`
passes again.
